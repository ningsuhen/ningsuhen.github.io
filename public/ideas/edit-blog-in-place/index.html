In 30 seconds

  • Fixing one word on a static blog means finding the repo, the file and the line, then a pull request and a deploy.
  • The idea: a browser extension that lets me edit my own post on the live page, then sends the change back to the Markdown as a pull request.
  • Astro makes the way back easier. Its URLs come from file names, and its Markdown build can say which lines each paragraph came from.
  • When the extension can't find the lines, an AI coding agent gets the before and after text and makes the edit.
  • I'm building a rough version for this site. It isn't finished, and I haven't measured anything.

The problem

My blog is Markdown files in a GitHub repo. Astro builds them and GitHub Pages serves the result. That setup is cheap and simple, until I want to fix one word.

Then I find the repo, then the file, then the line. I edit the Markdown, open a pull request, wait for the checks and the deploy, and look at the page again to make sure it reads right.

GitHub's web editor helps with the editing part. Pressing the period key on a repository opens it in an editor in the browser (source). But I'm still editing raw Markdown, in a different place from where I saw the typo, and I still have to find the file.

Most of the time the fix is one sentence. The trip around it is the cost.

Principles

  1. Edit where you read. The page I'm reading is the editor.
  2. Change only what I touched. The rest of the file stays as it was, byte for byte.
  3. Show the diff first. Nothing goes to GitHub until I've seen the Markdown change.
  4. Every change is a pull request. It can be checked, closed or reverted like any other.
  5. The repo decides when it merges. Required checks gate the merge, not the extension.
  6. Hand it over instead of guessing. When the source can't be found, an agent gets the edit. The extension never writes to lines it isn't sure of.
  7. Only on sites I allow. The extension stays quiet everywhere else.

Finding the source

The hard part is the way back: from a paragraph on the page to the lines in a file. I see three ways, from most exact to least.

  1. The site says. A small build plugin marks each rendered block with the source lines it came from, and the page names its source file. The extension reads that and knows exactly which lines to change. This needs one change to the site.
  2. The extension guesses. On an Astro site the URL points at a likely file (see Why Astro). The extension fetches that file and matches the page's paragraphs against it by their text. If the text never matches, the guess was wrong and it stops.
  3. An AI coding agent. When neither works, for example inside an MDX component or on a site built some other way, the extension hands the before and after text to an agent. The agent finds the source, makes the edit and opens the pull request itself.

Small diffs

Going from a rendered page back to Markdown loses things. Curly quotes, how the lines were wrapped, whether a word used underscores or asterisks for emphasis. If the extension rewrote a whole paragraph from the page, every edit would change more than it should.

So it compares instead. It turns the paragraph back into Markdown before and after the edit, takes the difference, and applies only that difference to the real source lines. Text I didn't touch keeps its original spelling. When the difference won't apply cleanly, it rewrites that one block, and the diff shows it.

Code, math, tables and images don't survive a trip through the page. Those open as Markdown in a small box instead of being edited in place.

Publishing and merging

Publish creates a branch, commits the changed file and opens a pull request. Then it turns on GitHub's auto-merge for that pull request.

Auto-merge merges a pull request after all required reviews and status checks pass. It has to be enabled for the repository first (source). One detail matters here. GitHub only offers auto-merge on pull requests that can't be merged right away. If the repo requires no checks, there is nothing to wait for, so the checks only gate the merge if the repo requires them.

On this site the required checks are the build, a link check and a leak scan. A failed check leaves the pull request open, and nothing reaches the live site.

The commit is made against the exact file I was shown. If that file changed in the meantime, for example from another edit, the extension stops instead of overwriting it.

URLs come from files

Astro builds its URLs from the files in src/pages/. Markdown and MDX files there become pages on their own (source). So a page at /about/ could come from src/pages/about.md, and the URL alone is a good guess for the file.

Content collections

Blog posts usually live in a content collection instead. Astro gives each entry an id made from its file name, unless the entry sets its own slug (source). Astro makes no pages for a collection by default, so the site's own route decides the URL. On many blogs that route is something like /posts/<id>/.

That is enough for a guess. The last part of the URL names the file, and the part before it often names the collection. The guess is never trusted on its own: the page's text has to match the file before any line is touched.

Knowing it's Astro

Astro exposes its version as Astro.generator, and the docs show it used in a <meta name="generator"> tag (source). Some sites print that tag, so the extension can tell it's on an Astro site.

It is opt-in. A site that leaves it out still works with the first and third ways to find the source.

Line numbers from the build

Astro's Markdown build accepts plugins (source). The syntax tree a Markdown parser builds records where each piece sits in the source file (source). So a small plugin can stamp every rendered block with its first and last line. That makes the first way exact.

Which plugins

Since Astro 7 the default Markdown processor takes its own plugin list. Sites that use the unified processor take remark plugins. I've only tried the unified one.

Other site builders

Hugo, Jekyll and the others have their own rules for where pages come from. I haven't looked at them. For now the AI coding agent is the only way to edit those.

Who can do what

An extension puts its code into a page with content scripts. Those run in an isolated world, so the page's own JavaScript can't see the extension's variables (source). That is why the GitHub token stays with the extension. The page only ever gets results back.

Who can do what
WhoCanCan't
The pageShow its text, which I then editRead the token or talk to GitHub
The extensionRead the source, open a branch and a pull request, turn on auto-mergeSkip the repo's required checks, or run on sites I didn't allow
The repoRun its required checks and hold the merge until they passCheck anything before the branch is pushed
MeSee the diff first, close or revert the pull requestTake back a pushed branch on a public repo (see below)

I'd use a fine-grained token limited to the blog's repository. GitHub lets you limit a token to specific repositories (source). The extension should only run on sites I name, and its right-click item can be limited to matching pages too (source).

Public before the checks

The diff is the real last check

My blog's repo is public. GitHub puts it this way: "The code will be visible to everyone who can visit GitHub.com" (source). That includes the branch the extension pushes, before any check runs. A leak scan can stop a mistake from reaching the live site, but it can't stop it from being seen.

Glossary

GitHub Pages

GitHub's static site hosting. A user site lives at <owner>.github.io and a project site at <owner>.github.io/<repository>.

Astro

A site builder that turns Markdown, MDX and its own components into static pages. Its docs show deploying to GitHub Pages with a GitHub Actions workflow.

Content collection

A set of related entries of the same shape, such as blog posts. Each entry's id comes from its file name unless it sets a slug.

Frontmatter

The block of fields at the top of a Markdown file: title, date, tags. It is not part of the body, so editing a paragraph doesn't touch it.

Syntax tree

What a Markdown parser builds from the text. Each piece records where it starts and ends in the source file, which is what makes line numbers possible.

Build plugin

A small function that runs while the site is built. Here it would stamp each block with the source lines it came from.

Pull request

A proposed change on its own branch. It can be checked, discussed, merged, closed, and reverted after merging.

Required status check

A check a protected branch insists on before a merge, such as a build. It has to pass, or be skipped or neutral.

Auto-merge

A GitHub setting that merges a pull request on its own once its required reviews and checks pass. The repo has to allow it.

Content script

Extension code that runs inside a web page, so it can read and change what's on it.

Isolated world

The private space a content script runs in. The page's own scripts can't see into it.

Fine-grained token

A GitHub personal access token that can be limited to specific repositories and permissions.

Diff

The lines a change removes and adds, side by side. Here it's shown before anything is sent.

Check yourself

Four questions. Pick an answer and the explanation opens. Nothing is stored.

1. I fix a typo with the extension. What changes in the repo?

Answer

The second. The source is the Markdown, and the extension changes only the lines it can tie to the paragraph. The site is rebuilt from the source after the merge.

2. Why is Astro a good first target?

Answer

The second. File-based routing and file-name ids make the guess possible, and the page's text confirms it. The generator tag is opt-in, so not every Astro site prints it.

3. The repo is public and I paste a secret by mistake, then press Publish. When can others see it?

Answer

The second. A public repo's branches are visible to anyone on GitHub. The leak scan only keeps the mistake out of the live site. That's why the diff comes first.

4. The repo requires no checks. What happens with auto-merge?

Answer

The second. GitHub only offers auto-merge on pull requests that can't be merged right away. The checks gate the merge only if the repo requires them.

Open problems

  • Other people's sites. I've only looked at mine. I don't know how often the text matching finds the right lines on other Astro blogs.
  • Custom domains. On <owner>.github.io the address names the account that owns the site. A custom domain doesn't, so the extension needs another way to find the repo.
  • MDX, frontmatter and images. An edit inside a component, a new title or date, or a new image doesn't map to a paragraph's lines. Today those go to the agent.
  • Stale pages. Right after a merge, the live page can be older than the source for a few minutes. An edit made then stops and has to wait for the deploy.
  • More than one author. If two people edit the same post at once, the second edit stops. I haven't worked out what should happen next.
  • Faster or not. I haven't timed this against the web editor, so I can't say it saves time.

What is not decided

  • Whether the build plugin should be the default, or the text matching is good enough on its own.
  • How much the AI coding agent may change beyond the exact edit.
  • Whether every edit should bump an "updated" date on the post.
