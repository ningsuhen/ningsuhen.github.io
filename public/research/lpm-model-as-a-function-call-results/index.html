LPM: a small model as a function call, performance and results so far · created 2026-10-26 · updated 2026-10-26

LPM is a Rust engine that runs a small language model on the GPU as a primitive you call from a program. Its WGSL shaders run unchanged on native Metal and in Chrome WebGPU. This page reports what I measured in the first three milestones, the eight lessons that cost time getting there, and which numbers were taken on a busy machine.

The question

Can a 0.1 to 0.6 billion parameter model run on the GPU fast enough, and from one shader source, to be called like a function from ordinary Rust code, natively and in a browser?

Status

Correct on both targets: both models match a float32 reference. Not yet fast enough: the decision latency target is missed by a factor of 13.5. Loading a 1.4 GiB model in the browser takes 16 to 26 seconds on the machine I used.

How to read it

Lower is better for every time. Each row names the model, the target and the load. Rows marked contended were measured while other jobs shared the GPU, so treat them as upper bounds. I did not re-run anything for this page; every number comes from the project notes.

What it is and why

The idea is a model call that behaves like a function call. A program asks a typed question ("which department should handle this ticket?") and gets back a decision with a margin, not a chat reply. The engine owns its runtime and its kernels, so there is no ML framework in the hot path. The kernels are written once in WGSL. Native Metal runs them through wgpu, and Chrome runs the same source through WebGPU. The weights ship inside the program as one file.

Two design choices explain most of the measurements below. First, a decision reads back 16 bytes (the two best candidate ids and their margin, computed on the GPU), because in a browser every readback is a trip to the GPU process. Second, a decision is a prefill and not a generation: the engine keeps the instruction's KV cache on the device and runs only the new tokens. That makes prefill, not per-token decode, the hot path.

Method

Machine
One laptop-class Apple M4 Max with 128 GiB of unified memory, macOS 26.5. Native runs use the Metal backend of wgpu. Browser runs use Chrome for Testing 156 (headless, WebGPU on the same Metal GPU). No other machine and no other GPU vendor.
Models
SmolLM2-135M and Qwen3-0.6B, both base models, run in fp16. The references are float32 greedy outputs dumped with the Hugging Face stack, and a separate candle (Rust) implementation that serves as the speed baseline.
Load
The GPU was shared with unrelated training and inference jobs for much of the work. The notes record the 1-minute load average for some runs (up to 330). Rows say contended, quiet or not recorded. Quiet means a load average of about 9. The notes do not give one rule for quiet, so I use their label.
Milestones
M0 is the foundation, M1 is decode on the GPU, and M2 is the single-file artifact that loads in a browser. The notes also call the test-bench work the testbench.
Gates
Correctness is "greedy tokens equal the float32 reference up to the first near-tie". A near-tie is a step where the reference's top-two margin is under 0.05, so a flip there is legitimate. Each result below names its test or probe in the claim table.
T_trans
The round trip of an empty submit: send a command buffer, wait for the GPU to report done, with no kernel work. The null-kernel floor is the marginal cost of one more trivial dispatch in the same submit.
Reference decide
Qwen3-0.6B, 300 static instruction tokens (prefilled once and kept), 30 dynamic tokens in one batched pass, 4 single-token candidates, warm, p50 over 50 runs.

What I learned

Eight things cost time getting the one shader set to run on Metal and in Chrome. Each is in the Learnings tab, with its evidence and its cost.

  1. One WGSL source works, and the price is paid in the browser's rules and in the features it lacks.
  2. A 1.5 ms "transfer time" was the wait call's 1 ms sleep, not the GPU. Report the statistic and the load with every latency.
  3. A zero in the output meant the kernel never ran. I blamed the wrong thing twice before I found the missing device feature.
  4. I did not adopt a kernel DSL: faster on Metal, broken in Chrome for a reason that was fixable, and not my bottleneck.
  5. One small call, write_buffer, kept the wasm heap flat. The obvious call copied the whole model into it.
  6. Chrome's HTTP cache will not keep a 600 MiB response. OPFS will, and it only counts if it survives a real reload.
  7. On a busy machine, compare kernels in pairs inside one process, and still read the spread.
  8. Compare greedy tokens to a golden with the reference's own margin at each step, not with a token count.

The decision: 16-byte readback, and latency against its target

The decision call returns the top-two ids and their margin in 16 bytes. On SmolLM2-135M, prompt 0, step 0, the GPU margin was 1.0312 against the reference's 1.0317. With candidates, the vocabulary head gathers only the candidate rows: for Qwen3-0.6B that is 8 KB of weights read instead of 311 MB. Candidate top-two equals full-vocabulary top-two, and the candidate logits are bit-identical to the full head's for those rows. Reusing a prefilled prefix is bit-identical to prefilling the whole text again. The batched pass differs from the single-token path by at most 0.0156 in logit, with no flipped decision.

The first suspicion was launch overhead, which would argue for fusing kernels. 1. One WGSL source for Metal and Chrome, and what it cost

Why. I chose wgpu with hand-written WGSL as the primary backend because the development Mac runs the browser's exact shader language natively. Two of the three targets then work on day one, and one correctness test covers both. It paid off early. SmolLM2-135M and later Qwen3-0.6B decode 64 tokens identically to the float32 reference on Metal and in Chrome from the same source.

What it cost. Chrome enforced rules that Metal did not. The first browser run needed three fixes, none of which touched the Metal path:

  • WebGPU caps a uniform buffer binding at 64 KiB. I had asked for 128 KiB and now bind each 256-byte slot with an explicit size.
  • A blocking readback deadlocks wasm. On the web backend the poll call does nothing and the map callback is a JavaScript promise that fires only when the event loop is free, so a thread that blocks on it waits forever. The wasm build now awaits a future; native keeps the blocking path.
  • A GEMV kernel returned early before a workgroupBarrier(). Chrome's WGSL validator rejects that as non-uniform control flow and Metal accepts it. A valid flag now lets every thread reach the barriers.

Two limits shaped the loader from the start. Chrome allowed a 128 MiB storage binding and a 256 MiB buffer on this machine, so the loader design caps each weight buffer at 128 MiB. A wasm module is capped at 1 GiB (see lesson 5). A third came with the larger model: Qwen3's vocabulary of 151,936 rows is more than the 65,535 workgroups allowed per dispatch dimension, so the logits kernel spans a 2D grid. That change also applies on native.

The price in speed. The browser path cannot use hardware lane operations through this stack, because wgpu's web backend does not map the subgroups feature (lesson 3). The milestone notes report that a subgroup-reduce version of the matrix-vector kernel cut a decode step from 19 to 33 ms down to 9 to 15 ms on Metal. They give neither model nor load, and I did not re-check it. That version is native-only. The rule I adopted is to choose the kernel variant explicitly by target and fail closed, never to fall back silently. Native Metal therefore has a faster variant that Chrome cannot run.

What I would repeat

Start with the kernel that runs everywhere and add native speedups behind an explicit per-target switch, so the shared kernel stays the reference.

2. The poll spin that inflated transfer time

What happened. An early test showed one dispatch costing 1.7 ms, and a decode loop that looked bound by round trips. I timed an empty command buffer, with no GPU work at all, three ways on Metal.

Round trip of an empty submit, native Metal, clean window (load not printed, test kept in the repo as a root-cause record).
How completion was detectedLatency
wgpu poll(Wait) (the old decode loop)1372 µs
wgpu poll(Poll) in a spin, no sleep206 µs
Metal's own waitUntilCompleted21 µs

Cause. In the wgpu Metal layer, wait checks the command buffer status and sleeps for 1 ms between checks, so completion shows up about 1.5 ms late. The GPU and Metal were fine. The 1.7 ms "per dispatch" was this wait. The decode loop now spins on poll(Poll), and every native hop between code and model sees completion in microseconds.

What it cost. The spin burns a core, and under load it loses its advantage. A later measurement of the empty round trip on Metal gave a p50 of 610 µs and a p99 of 40,293 µs at a load average of 112 (the machine sat between 100 and 258). That looked like a regression from 206 µs. It was not: 206 µs was a clean-window mean and 610 µs was a loaded-machine p50. The test header now says so, and the notes tell us to re-measure below a load of 20. The same lesson hit the browser. The first Chrome T_trans was inflated by a console.log inside the timed loop, so the hot-path logging is now behind a constant that is false and compiled out.

Lesson. Write the statistic (mean, p50, p99) and the load next to every latency, and take a floor measurement that does not depend on your own stack (here Metal's own wait) before you trust a number from it.

3. The subgroups and shader-validator gotchas

What happened. Subgroup operations looked unusable in Chrome, three times for three different reasons. Each time the symptom was real and the diagnosis was wrong.

  1. The first browser probe reported that Chrome rejects enable subgroups;. A re-check requested subgroups in the device's required features and the shader compiled, in installed Chrome 155 and in Chrome for Testing 156. The original probe had created the device without the feature.
  2. A CubeCL matrix-vector kernel read back all zeros in Chrome. First I blamed its WGSL code generation, then Chrome's subgroups, which I guessed were degenerate. Neither held. The generated WGSL, captured from the library's own log and run raw in Chrome, matched the CPU reference. A hand-written subgroupAdd probe was correct, with a subgroup width of 32 inferred from the result pattern.
  3. The real cause was a missing device feature. wgpu's web backend maps only 16 features, and Subgroups is not one. The device was created without it, Chrome refused the shader at module creation ("extension 'subgroups' is not allowed in the current environment"), the kernel never ran, and the output buffer stayed zero.

The validator cousin. The early-return-before-barrier rule in lesson 1 is the same class of problem: a rule Chrome enforces strictly and Metal does not. A related native quirk goes the other way. Chrome needs enable subgroups; at the top of a shader, but the naga version I use natively rejects that line, so the source gets a per-target prefix.

What it cost. The browser build cannot use subgroupAdd until wgpu's mapping and the vendored bindings are patched, which is an open item that needs the owner's decision because the proper fix is an upstream pull request. Until then the shared-memory reduction is the Chrome kernel.

Lesson. An all-zero output usually means the kernel never ran. Check for a captured validation error first. Capture the exact shader that ran and run it on its own before you blame a code generator. Request every feature on the device that you test with.

4. Why I did not adopt a kernel DSL

The spike. I ported the fp16 matrix-vector kernel and the decode attention kernel to CubeCL, a Rust kernel DSL, and compared them with the hand-written WGSL. The kill rule was: drop it if it is more than 1.2 times slower, or if Chrome rejects it.

On Metal at low load CubeCL was faster on every kernel. At high load the matrix-vector ratio crossed 1.2, but only because CubeCL issues 211 separate launches while the WGSL path encodes them into one command buffer. The CPU time to issue those launches was 0.227 ms at load 30 and 1.0, 8.7 and 61.6 ms at loads of about 95, 105 and 190. In Chrome the hot kernels never ran, for the missing-feature reason in lesson 3.

The verdict. Not adopted. Three things carried it. It would put a second compiler between me and a running kernel, which is how the predecessor died. Its browser path was blocked on a gap I could not close without patching wgpu. And the speed advantage was partly my own naive kernel: my attention kernel was badly written at first (one thread per head, scores recomputed), and in a separate test the milestone notes report that a hand-unrolled 64-wide dot product took one test position from about 3.0 ms to 0.44 ms with no DSL (model and load not stated, not re-checked). The gap I saw was real, and part of it was a kernel I had not tuned yet.

What the review taught us. The first write-up of this spike was wrong in several places and a review fixed it. The benchmark timer started after the launches, so GPU work went untimed. The decode step was modelled as 8 matrix-vector kernels times 30 layers plus one attention, when it is 7 per layer plus one logits kernel and 30 attention calls. "CPU-launch-bound" held only above a load of about 60. And the root cause for Chrome had been mis-assigned to code generation. The conclusion survived, the evidence needed rebuilding.

Caveat that stays. One note and the plan still describe the Chrome failure as a CubeCL lowering problem. The later note corrects it to a device-feature gap. I follow the later one.

5. The weight-streaming upload that kept the wasm heap flat

The problem. Qwen3-0.6B is 1.43 GB. In the first browser attempt the model hung silently at the packing step after fetching the whole file, because the loader copied all of it into wasm linear memory. A wasm module is also capped at 1 GiB, so the single-file artifact cannot be compiled whole: the control test failed with "size > maximum module size (1073741824)" on a 1.26 GB module.

Why they differ. JavaScript cannot reach the raw GPUBuffer that wgpu owns, because the handle is a private field. The only write path there is map then write, and that path copies the whole mapped range into a wasm-heap vector. The heap does not shrink when the vector is dropped, so the 256 MiB stays for the life of the page. write_buffer instead hands the chunk to the browser as a view over wasm memory, not a copy, so the heap stays at about 16 MiB plus the module. I checked three byte ranges against the source file after the 256 MiB and 1.2 GB runs, and all matched.

What it gave us. The shipped loader keeps the raw file in the browser, converts one 16 MiB chunk at a time in place, and writes it to the GPU. Qwen3-0.6B now loads in Chrome with the wasm heap at 18 MiB, and the 1.4 GiB demo at 17.3 MiB, both under the 64 MiB gate. I did not try to reuse one GPU staging buffer with copyBufferToBuffer, because an unfenced reuse races the copy in flight.

What I do not know. The 15 GB/s above is the synthetic path. The real demo's cold stream phase took 25.7 s for 1.4 GiB, about 58 MB/s, and the notes do not split that gap between verification, the OPFS write and a shared GPU.

6. Browser cache behaviour: OPFS against the HTTP cache

The question. A second visit should not download 1.4 GiB again. The design debate claimed that Chrome's HTTP cache drops a single response over about 500 MiB. I tested it, with a 1 MiB control to prove the method.

Reload after a full fetch, Chrome on the M4 Max, values as reported in the testbench notes and not re-checked, served with Cache-Control: max-age=3600. Chrome version for this probe not recorded; load not recorded.

600 MiB629,157,949Not kept (re-downloaded)

The signal is Resource Timing's transferSize: zero on a cache hit, the full body on a miss. Wall time misleads. The reload ran at about 2 GB/s anyway, because the operating system's page cache served it, not Chrome's HTTP cache.

OPFS (the origin private file system) kept the 600 MiB as 38 shards of 16 MiB named by their BLAKE3 hash. Browser storage usage went from 0 to 629,168,061 B. Writing took 916 ms end to end, about 0.69 GB/s, of which the fetch alone was 323 ms. After a real reload, reading all 38 shards back took 202 ms, 3.12 GB/s, and three byte ranges matched the file. These OPFS figures are likewise as reported in the testbench notes, not re-checked by us.

The bug my first version had. The first demo remembered the cache file name in memory, so a warm reload worked only inside one page session. A real reload lost it. The fix tees the code prefix to OPFS too, looks the cache up at start-up, and recompiles the module from the cached code. The probe now does a true page reload and asserts zero requests to demo.wasm afterwards. A cache test that never reloads the page does not test a cache.

What the numbers do not yet explain. By the storage numbers, reading 1.4 GiB should take about half a second (1.4 GiB at 3.12 GB/s, my arithmetic). The measured warm loads took 23.6 s, 16.0 s after a reload, and 12.4 s for a device-loss re-upload, on a shared GPU. So the warm path is bound by the upload and verification, not by storage. I have not isolated which.

7. The paired A/B ratio for noisy-machine kernel comparisons

The problem. The GPU was shared with unrelated jobs, and the load average stayed around 330 for an hour at one point. A baseline measured earlier at "the same load" did not hold, and CubeCL's matrix-vector ratio swung from 0.335 to 3.2 as load changed.

The method. Run baseline and candidate in the same process, interleaved ABAB for at least 10 rounds, and report the median of the per-round ratios with the spread. Load drift hits both arms in a round alike, so it cancels in the ratio. Absolute throughput is recorded, but only as contended. I made this the standard for every kernel comparison on a busy machine.

Where I used it. The matrix-multiply kernel with vec4<f16> loads against the scalar-load one, Qwen3-0.6B shapes, native Metal, 12 rounds, contended:

1.330
median ratio, scalar time over vec4 time
0.336 to 2.348
spread across the 12 rounds
7 of 12 rounds favour vec4

Read it honestly. The median says vec4 is about 33% faster. The spread says single rounds disagree by a factor of seven. Seven of twelve is what a fair coin gives about 39% of the time (one-sided, my arithmetic), so the rounds alone do not settle it. I kept vec4 because it passed the correctness gate and cuts global load instructions by four, and I wrote down that a clean-window re-measure is needed before anyone calls it a win. The method removes drift. It does not remove noise.

The method is also not a substitute for the right diagnosis. Before it, a separate three-way experiment showed the matrix multiply was kernel-bound: launch overhead was 6% of its cost (61.7 µs per dispatch against 979.4 µs per GEMM). That told us to tune the kernel, not fuse launches.

8. Near-tie handling when comparing greedy tokens to a golden

The problem. The engine runs in fp16 and the reference is float32. Over 64 greedy steps the two will disagree wherever the reference's top two tokens are almost tied, and that is fine. A real bug also looks like a disagreement. The gate has to tell them apart, or it either fails on noise or hides defects.

What I got wrong first. The first version of the native comparison counted a divergence as a near-tie if the reference's top-two gap was small. That let a mismatch pass whenever the engine picked a token that was not the reference's runner-up. The review's fix: measure logit[top1] - logit[golden token] under the reference's own logits, require it under 0.05, and add a unit test that forces a non-runner-up mismatch and asserts failure. The comparison also fails closed on the manifest: it hashes the loaded weights and checks the dtype and device the golden was made on.

The second trap. A token count is a bad proxy. In the SmolLM2 set, 69 of 100 prompts have at least one step with margin under 0.05, so a rule like "at least 8 tokens must match" would be wrong in both directions. The gate keys on the per-step margin, which the golden dump stores for every step.
