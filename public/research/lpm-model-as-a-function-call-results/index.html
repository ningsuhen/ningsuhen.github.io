LPM: a small model as a function call, performance and results so far · created 2026-10-26 · updated 2026-10-26

LPM is a Rust engine that runs a small language model on the GPU as a primitive you call from a program. Its WGSL shaders run unchanged on native Metal and in Chrome WebGPU. This page reports what we measured in the first three milestones, and says which numbers were taken on a busy machine.

The question

Can a 0.1 to 0.6 billion parameter model run on the GPU fast enough, and from one shader source, to be called like a function from ordinary Rust code, natively and in a browser?

Status

Correct on both targets: both models match a float32 reference. Not yet fast enough: the decision latency target is missed by a factor of 13.5. Loading a 1.4 GiB model in the browser takes 16 to 26 seconds on the machine we used.

How to read it

Lower is better for every time. Each row names the model, the target and the load. Rows marked contended were measured while other jobs shared the GPU, so treat them as upper bounds. We did not re-run anything for this page; every number comes from the project notes.

What it is and why

The idea is a model call that behaves like a function call. A program asks a typed question ("which department should handle this ticket?") and gets back a decision with a margin, not a chat reply. The engine owns its runtime and its kernels, so there is no ML framework in the hot path. The kernels are written once in WGSL. Native Metal runs them through wgpu, and Chrome runs the same source through WebGPU. The weights ship inside the program as one file.

Two design choices explain most of the measurements below. First, a decision reads back 16 bytes (the two best candidate ids and their margin, computed on the GPU), because in a browser every readback is a trip to the GPU process. Second, a decision is a prefill and not a generation: the engine keeps the instruction's KV cache on the device and runs only the new tokens. That makes prefill, not per-token decode, the hot path.

Method

Machine
One laptop-class Apple M4 Max with 128 GiB of unified memory, macOS 26.5. Native runs use the Metal backend of wgpu. Browser runs use Chrome for Testing 156 (headless, WebGPU on the same Metal GPU). No other machine and no other GPU vendor.
Models
SmolLM2-135M and Qwen3-0.6B, both base models, run in fp16. The references are float32 greedy outputs dumped with the Hugging Face stack, and a separate candle (Rust) implementation that serves as the speed baseline.
Load
The GPU was shared with unrelated training and inference jobs for much of the work. The notes record the 1-minute load average for some runs (up to 330). Rows say contended, quiet or not recorded. Quiet means a load average of about 9. The notes do not give one rule for quiet, so we use their label.
Milestones
M0 is the foundation, M1 is decode on the GPU, and M2 is the single-file artifact that loads in a browser. The notes also call the test-bench work the testbench.
Gates
Correctness is "greedy tokens equal the float32 reference up to the first near-tie". A near-tie is a step where the reference's top-two margin is under 0.05, so a flip there is legitimate. Each result below names its test or probe in the claim table.
T_trans
The round trip of an empty submit: send a command buffer, wait for the GPU to report done, with no kernel work. The null-kernel floor is the marginal cost of one more trivial dispatch in the same submit.
Reference decide
Qwen3-0.6B, 300 static instruction tokens (prefilled once and kept), 30 dynamic tokens in one batched pass, 4 single-token candidates, warm, p50 over 50 runs.

The attention kernel was the whole problem. It ran with a workgroup of one thread, so nine threads worked on the entire GPU, and it recomputed the query-key score inside an inner loop. Readback, allocation, weight upload and per-op submits were each checked and were cheap. Giving the kernel 64 threads per head made decode 18 times faster on Metal. The notes also report a Chrome speed-up of the same size (18.4 s to 1.0 s) without naming the model or the load, and we did not re-check it.

The old target of 6 ms per token for decode was retired. A program that wants a decision needs a forward pass over the instruction and the input, not a token stream, so the project measures decisions instead.

The decision: 16-byte readback, and latency against its target

The decision call returns the top-two ids and their margin in 16 bytes. On SmolLM2-135M, prompt 0, step 0, the GPU margin was 1.0312 against the reference's 1.0317. With candidates, the vocabulary head gathers only the candidate rows: for Qwen3-0.6B that is 8 KB of weights read instead of 311 MB. Candidate top-two equals full-vocabulary top-two, and the candidate logits are bit-identical to the full head's for those rows. Reusing a prefilled prefix is bit-identical to prefilling the whole text again. The batched pass differs from the single-token path by at most 0.0156 in logit, with no flipped decision.

Native T_trans misses its 50 µs target by either number, 610 µs contended or 206 µs in a clean window. Metal's own wait costs 21 µs, so most of the gap is in how completion is detected, not in the GPU. The browser round trip is under its 2 ms target, with 1.8 ms at the worst p99 we recorded. On native the empty round trip is measured directly. In Chrome on_submitted_work_done does not fire for an empty submit, so T_trans there is derived as one dispatch minus the marginal dispatch cost. The two are the same quantity but not the same measurement.

The first suspicion was launch overhead, which would argue for fusing kernels. The experiment ran the same pass three ways: real GEMMs, the same workgroups through an empty kernel, and no GEMMs. Launch overhead came to 6% of the GEMM cost, so the kernels themselves are the limit, and fusion is not the next lever. The project's rule of switching to Metal-specific kernels if the GEMM stays under 1.5 TFLOPS has not been decided, because the 0.13 TFLOPS figure predates the tuning and the tuned kernel has only a contended ratio. The project parked the GEMM until the GPU is quiet.

These runs used Qwen3-0.6B: the demo page loads the Qwen3 golden tokens and the pack carries the Qwen3 model id. They were headless Chrome on the same M4 Max with the GPU shared, so we treat the load times as contended: the notes say load times are recorded as contended, and the result file stores no load average. The spread between the three re-upload times (23.6, 16.0 and 12.4 s) is the clearest sign that these are noisy. Cold load is slow compared with the 1.6 GB/s a synthetic 1.2 GB stream reached in an earlier test, but the artifact path also verifies a BLAKE3 hash and writes the OPFS cache, and the notes do not split those costs out.

Failure paths were tested too. A corrupted cache gives "BLAKE3 mismatch", a truncated one gives "stream ended early", and a missing cache disables the warm path. None of these falls back silently. A software GPU adapter (SwiftShader) is refused at start-up, and a real GPU is not.

One more number that is easy to misread: the claim of zero allocations per token is narrower than it sounds. The measured gate is zero GPU-resource creations over 64 decode steps. The host still makes about 4268 allocations per token (the count does not grow between two equal windows), and each decode step is two encoders and two submits.

  1. 1Where the notes disagree

Where the notes disagree

We found these while cross-checking. We kept both numbers and did not pick one.

  • SmolLM2 decode on Metal is 24.3 ms per token in the milestone notes and 10.6 ms median in the later test-bench notes. The first records no load and no build profile; the second is a release build at load 9. The gap is probably load, build profile or both, but the notes do not say.
  • The test-bench notes say the engine is "about 3.5 times slower" than candle. Dividing their own numbers gives 3.4 for SmolLM2 (328.1 / 95.1) and 4.3 for Qwen3 (138.8 / 32.3). The 3.5 fits only the small model.
  • The Chrome decode after the fix is 1.0 s in one note and 2.3 s in another. The second includes weight upload. Neither records the load.
  • The paired-ratio run says "load average about 110 to 116" in its result and "the load has stayed about 330 for an hour" in its rationale. We report both.
  • Per-dispatch cost appears as about 40 µs (a spike note, load not recorded), 61.7 µs (launch overhead under load) and 110 µs (null-kernel floor at load 112). They are three different tests. We do not know which one to expect on a quiet machine.
  • The wasm heap is 18 MiB in the M1 notes and 17.3 MiB in the M2 result file. The raw byte count (18,087,936) is 17.25 MiB, so the 18 is a rounding up.
  • The reference decide is 135 ms p50 in one line and "104 ms of 140 ms" in another for the same step. The notes do not say whether 140 is a different statistic or a different run.

What this does not show

Read this first

One machine, one run per number, no repeats with error bars, and no other GPU vendor. Many timings were taken at a load average of 100 to 330 on a shared GPU. Treat every contended row as an upper bound and not as the engine's speed.
  • Single machine: an Apple M4 Max. Nothing was run on an Intel, AMD or NVIDIA GPU, on Windows or Linux with a GPU, or on a phone. The Linux build was checked only for embedding and hash verification, with no GPU.
  • Single run per number. The only statistics are p50 and p99 over repeated calls inside one run, plus one 12-round paired ratio with a wide spread.
  • Base models only. We used SmolLM2-135M and Qwen3-0.6B as published. No fine-tuned head, no module and no quantisation was measured here.
  • Accuracy is not measured here. "Matches the float32 reference" is an equivalence check, not a quality score. We say nothing about how often a decision is right on a real task.
  • The decision latency target is missed (135 ms against 10 ms on Metal) and the Chrome figure was never measured. Do not read this page as showing a usable decision latency.
  • Browser numbers come from headless Chrome for Testing, not from a user's browser. Chrome leaves the adapter description empty, so the GPU is identified only by vendor (apple), architecture (metal-3) and "not a software fallback".
  • No comparison against another engine in the browser, and no memory-bandwidth number: the small models may sit in the system-level cache, so achieved GB/s would not be main-memory bandwidth.
