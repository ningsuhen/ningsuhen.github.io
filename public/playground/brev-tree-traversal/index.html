The question

Can a small encoder replace a large model if you hand it the intents as a tree of short questions?

What this tab is

A replay. Every probability below was recorded from a real laya run on the 3,080 Banking77 test messages (data cut 2026-10-24). No model runs on this tab and there is no box to type your own message; the Speed test tab runs laya live, for timing.

How to read it

At each node laya scores every option; the walk follows the highest one. A wrong turn near the top cannot be undone further down.

Walk the tree

Sample, not benchmark

These are 60 of the 3,080 test messages, chosen with seed 42: 10 correct, 10 wrong at the root, 10 wrong lower down, 10 with the lowest margins, and the 20 shortest. Errors are over-represented on purpose, so do not read accuracy off this list. Message text is public Banking77.

    The verdict in the ledger

    laya as a substitute for the 27B is refuted: the walk lands 30.8 points below the 27B short prompt (95% CI 28.9 to 32.8). Its strength is speed and shortlisting, not this walk. Holding the lowest-margin 15% of walks for the 27B lifts the tree from 47.0% to 55.2% in the ledger.

    Replay check. Re-running the greedy walk from the recorded probabilities gives 1,447 of 3,080 correct, 46.98%, which matches the ledger's 47.0% for this tree.

    Three ways the walk fails

    It obeys the text, even when wrong

    8.9%

    Give each option a sibling's criterion, keep the names, and accuracy falls from 47.0% to 8.9% (38.1 points, 95% CI 36.3 to 40.0). laya follows the criteria text over the option name.

    Names alone are not enough

    36.8%

    Names only: 36.8%. Opaque ids with the criteria: 40.6%. Both: 47.0%. Dropping the criteria costs 10.2 points (95% CI 8.5 to 12.0). The criteria carry most of the knowledge.

    Wrong turns compound

    0.72 × 0.72 × 0.79

    Per-level accuracy in the ledger: 71.9%, 71.9% and 78.8% (level 3 over 2,200 messages). Multiplied, about 0.41. A wrong group at the root cannot be recovered below it, and raw beam search made it worse (40.5% against 47.0%).

      The question

      How quickly does laya run on a visitor's GPU in a browser, compared with the 8 GB RTX 4060 the benchmark used?

      Status

      Live. Everything runs in your tab. The 846 MB model is fetched only after you agree, once; later visits read it from your browser's cache.

      How to read it

      Lower latency and more decisions per second are better. The runtimes differ, so treat the comparison as an order of magnitude, not a ranking.

      Different runtimes, one checked GPU

      The benchmark's laya figure is PyTorch fp16 on an RTX 4060; this page runs an fp16 ONNX conversion in ONNX Runtime Web. That file matched native fp32 on 47 of 47 recorded passes on one GPU (Apple Metal, Chrome, ONNX Runtime Web 1.31-dev; not yet repeated on the 1.27.0 runtime this page now uses); the full-set parity run was not done.       Method

      • 20 fixed Banking77 test messages (seed 42; a different sample from the Walk tab's 60). For each, the page replays the recorded greedy walk down the same 23-node tree and runs one forward pass per node on the path: passes in all, each one question for one message at batch 1.
      • A run is 50 decisions, cycling through those passes in order. Three runs follow an untimed warm-up of three passes; the first warm-up pass, which includes shader compilation, is reported separately. A "walk" is the sum of the passes of one message; only walks that completed inside the 50 decisions count.
      • Inputs (token ids, masks, marker positions) were built offline with laya's own tokenizer and prompt code. Tokenisation is not timed and is not done in your browser, so this measures the model forward pass plus the result read-back from the GPU.
      • Each output is compared with what native ONNX Runtime on a CPU gives for the fp32 model, as a check that the browser computes the same thing. The page warns when fewer than 95% of top options match.
      • The model file is fetched from the public Hugging Face repository ningsuhen/laya-typed-decisions-onnx at run time (846,157,544 B, sha256 06405e8bae697839ee2654bef55b5fd26b3435ac479980e48da6cb6b777ce46a), and its length is checked before it is used. It is not part of this site.

      Caveats: the walk

      Read this first

      The Walk tab's scores are precomputed from one real laya run and replayed. Nothing on that tab calls a model, and there is no way to enter your own message.
      • One dataset (Banking77), one run, one authored tree. The result may not carry to other intent sets.
      • The 60 samples are stratified toward errors and short texts. They illustrate behaviour; they do not estimate accuracy.
      • Arms differ in model, prompt and hardware, so the comparison table is descriptive. Latencies are not like-for-like: laya ran locally, the 27B figure includes network and a shared queue.
      • The flat laya tournament used every fifth test message (n=616); its figure has a wider interval than the 3,080-message rows.
      • Bars show laya's option probabilities rounded to three decimals. Gold intents are the Banking77 labels. The tree was authored by a large language model, not tuned on these messages.
      • The per-level and compounding figures are the ledger's own, quoted as written; they were not independently re-derived on this page.

      Caveats: the speed test

      Different runtimes: not a like-for-like race

      The benchmark's laya latency (p50 ms) is a PyTorch fp16 greedy walk, several node passes per message, on an RTX 4060. The Speed test tab runs the fp16 ONNX file in ONNX Runtime Web, one forward pass per node. Compare per-pass with per-pass and per-walk with per-walk, and keep the runtime difference in mind.

      An fp16 conversion of laya, checked on a subset

      The file is an ONNX fp16 conversion in which the 30 attention IsNaN guards are rewritten as Not(Equal(p, p)) so they run on the GPU (same arithmetic). In Chrome with WebGPU on Apple Metal, under ONNX Runtime Web 1.31-dev, its top option equalled native fp32 on 47 of 47 recorded passes (largest probability difference 0.021). This page now runs the site's shared ONNX Runtime Web 1.27.0, and that browser check has not been repeated on 1.27.0. Natively, on a 134-message subset, 0 of 3,082 node decisions flipped and the final intent agreed on 134 of 134. The full 616-message parity run was not done. One GPU and one browser have been checked; yours may differ, which is why the page compares every output with native fp32.
      • Why not the smaller int8 file: under WebGPU it runs mostly on CPU kernels (all 122 MatMulInteger and 122 DynamicQuantizeLinear nodes were placed on the CPU provider) and it gave the wrong top option on 15 of 47 recorded passes (32%).
      • Thermal throttling and other tabs change the numbers; the first pass includes shader compilation. A software or integrated adapter will be far slower than a discrete GPU, and the page says so when it detects one.
      • The benchmark has no tokens-per-second figure for any model on the RTX 4060 and no FrogNano-4B run; FrogNano is not offered on this page, so its rows read "not measured".
      • The 846 MB download plus the GPU buffers needs a desktop or laptop with several GB of free memory. If the tab runs out of memory the page says so.
