  • Pressing the button first fetches the engine (about 0.3 MB) and a word list for the tokenizer (about 4.4 MB) from this site, then the model from huggingface.co, unless your browser already has it or you pick a file.
  • The engine is LPM, compiled to WebAssembly. It runs the model on your graphics card through WebGPU. There is no server and no fallback to software: without a real GPU you get a message, not a result.
  • Each call asks the model one closed question: given the instruction, the options and a few solved examples, which option letter comes next? Only the winner and the runner-up leave the GPU.
  • Margin is how far ahead the winner is over the runner-up, in the model's own units (a logit gap). Bigger means surer. It is not a percentage.
  • The prompt window is 2048 tokens. Every prompt uses all of the dataset's solved examples. Whether the answers are described by name, by definition or by both was picked per demo by accuracy on the dev split only; the test split never chose anything.
  • Dev and test are two separate sets of labelled items. The dev set picks the threshold. The test set is only used to report.
  • The keyword and regex baselines are hand-written rules, written from the label definitions before the dev and test texts were read. They run in your browser, like the model.
  • The test sets are small and the items are fictional. Treat the numbers as a demonstration, not a guarantee.

What this replaces

Today a person, or a pile of fixed mail rules, opens each incoming email and drags it to a folder: reply needed, meeting request, invoice or receipt, promo or newsletter, or FYI. Here the model picks the folder and three lines of code move the email.

The rules this demo follows:

  • The model only sorts into folders. Code never deletes, archives or auto-replies to any email, whatever the label.
  • Low-confidence predictions go to a 'Needs a look' folder for a human instead of a label folder.

    Use it in a program

    Call the model when an email arrives. It gives back one label and a margin. If the margin reaches your threshold, file the email in that label's folder. If not, put it in a "Needs a look" folder for a person.

    Email is private. The text stays on the machine that runs the model, there is no fee per email, and the time shown in the proof strip is the whole delay.

    What it must not be used for

    Never let the label delete, archive or answer an email: code only files it. Do not rely on it for mail where a miss is costly, such as legal notices or payment disputes, without a person. It was tested on fictional English emails only.

          What this replaces

          Today, often nobody checks: people paste emails, customer records and keys into a cloud chatbot and hope. Here a check runs first on your own machine, a plain regex check and the model, and the text may be pasted only if both say it is clean.

          The rules this demo follows:

          • Fail closed: the text is sent to the cloud assistant only when the model says clean with high confidence; anything else (personal-data, secret-or-credential, or low confidence) is blocked and the user is told why.
          • This is a speed bump to catch accidents, not a compliance control, and it must never be described as one.

            Use it in a program

            Run both checks. Block the text when either finds personal data or a secret, or when the model's margin is low. That is failing closed: doubt means no. Regular expressions are good at exact formats such as card numbers and keys. The model can read meaning. The table in the accuracy card shows what each one caught on the test split.

            The text being checked is the sensitive thing, so the check cannot send it anywhere. Running on the same machine is what makes it possible to check the text before it leaves.

              Use it in a program

              The pattern is the same as in the other tabs: call the model, read the label and the margin, and let ordinary code decide. A low margin means a person looks. Changing an answer or an example changes the prompt, so the engine reads it onto the GPU again on the next call (the one-time setup shown in the proof strip).

              There is no accuracy card here because there is no answer key. To know how often your setup is right you need a few dozen texts you have labelled yourself, set aside and never used as examples. The other tabs do exactly that.

              What it must not be used for

              A margin from one setup does not carry over to another. Do not act on answers alone for anything that matters until you have measured the setup on labelled texts.
