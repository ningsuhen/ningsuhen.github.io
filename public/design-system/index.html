Research · design system

Research Design System · created 2026-10-24 · updated 2026-10-24

Every research report, analysis page and exported artifact uses this. It is the ningsuhen.github.io theme: same palette, radius and width, light by default with dark support. Type and spacing are denser by default (see Density).

Compact is the default on purpose: this system is for technical papers and experiments, where density helps, while the main site stays reading-sized (16px, 1.7 line height).

Use it

<link rel="stylesheet" href="/design-system/research.css">
<html lang="en" data-theme="light">  <body class="rd-body">
  <main class="rd-container rd-prose"> ... </main>

Self-contained exports: inline the file's contents in a <style> tag instead of linking, and paste the page's lucide-sprite block (see Icons). Canonical source: public/design-system/research.css in the site repo. Everything is prefixed rd-, and type styles apply only inside .rd-prose, so it can't fight a report's own CSS.

Density

Three densities, one switch. Every size and spacing in the components reads a density token, so setting data-density retunes the whole page: compact (the default, on <html> or any wrapper), comfortable (roomier, close to the main site), dense (for wide data tables). Colours and radii do not change with density. The demo below is live: two wrappers, each with its own data-density, no reload.

Which density to use

  • compact (default): technical papers, benchmarks, experiments and dashboards. Most of the page is data; the default fits more of it on screen.
  • comfortable: essays, long-form reading and public write-ups, where the main site's 16px / 1.7 is the right feel.
  • dense: wide tables and data-heavy dashboards, where a 12px table is still legible (the floor is 11px). Pair it with rd-table-wrap--tall for long tables.

Put the switch on <html> for a whole page: <html data-density="comfortable">. Put it on a wrapper to change one block only.

Width

Default is the main site's content column: --rd-content-width: 54.5rem (872px, measured on the live site at a 1440px viewport; the site page is 75rem). That is .rd-container. Use .rd-container--wide (73rem = 1168px, the navbar's width: its content edges line up with the navbar card) only when the content needs it: a tabbed report with an "On this page" column, wide charts, dense tables, dashboards. Tables scroll inside their wrapper and never widen the page.

Theme contract

Light is the default and ignores the OS setting. Dark is <html data-theme="dark"> (or class="dark"). The site navbar is injected into every standalone page at build time; it reads and writes localStorage "theme" and sets data-theme for you, so a report needs no toggle of its own. Never read the OS preference to pick a theme. Use only the --rd-* variables for color so both modes work.

Footer rule: one small-print license block (12px, muted; copyright, permission, quotes, License · RSS · Sitemap) in a card no wider than the navbar (73rem). Never restyle it.

Icons (Lucide)

Icons are Lucide outlines, the site's icon language. Draw one with <svg class="rd-icon" aria-hidden="true"><use href="#i-file-text"/></svg>. The class sets the size (1.25em), stroke (currentColor, width 2, round caps and joins) and no fill, so an icon always matches the text beside it. Icons are never images and never a font.

Self-contained pages make no icon request: each page inlines only the symbols it uses, between the lucide-sprite markers. public/design-system/lucide-sprite.svg holds the union, for external reference.

To add an icon: reference #i-<name> (the name from lucide.dev) in the page, then run pnpm build or node scripts/build-lucide-sprite.mjs. The script reads @iconify-json/lucide, fails on an unknown name, and rewrites the markers. Nothing is hand-copied.

Experiment navbar

The in-page navigation for experiments and reports: rd-expnav, the bar under the navbar card. It sits --rd-navbar-gap (16px, the main site's rhythm) below the card, in the navbar's frame (--rd-navbar-width, 1168px from 1200px up). Its first link starts at the navbar's own left padding (the brand's edge: 152px at 1440px), and below 1200px at the container padding (16px). The navbar is sticky (like the main site), so the bar sticks one gap below it (top: calc(var(--rd-navbar-h) + var(--rd-navbar-gap))) and never sits under the card. Jump targets clear both (scroll-margin-top). Links scroll sideways inside the bar when they overflow: an edge fade shows the side with hidden links, and the scroll-spy keeps the active link in view. The section in view is highlighted (.is-active, aria-current) by a scroll-spy script with no dependencies. Smooth scrolling is on only when reduced motion is not requested. Links are plain anchors: they are keyboard reachable and show a focus ring.

<nav class="rd-expnav" aria-label="Sections">
<a href="#summary" class="is-active"><svg class="rd-icon" aria-hidden="true"><use href="#i-file-text"/></svg>Summary</a>
<a href="#method"><svg class="rd-icon" aria-hidden="true"><use href="#i-flask-conical"/></svg>Method</a>
</nav>

Put the nav directly under <body>, before <main>, so it spans the page. Each link targets a section header, <header class="rd-section__head" id="method">. The template has the nav and the script ready to copy.

Tabbed report layout

Long reports split into tabs. The tab bar and the content use the navbar card's width (--rd-navbar-width, 1168px from 1200px up), so their edges line up with the card above them. The tab bar sits 16px (--rd-navbar-gap) under the card, and its first tab starts at the card's brand edge (152px at 1440px). The "On this page" rail is outside that width, in the right page margin, the way the main post page's table of contents sits outside its column. Each tab has its own rail, listing that tab's sections.

Below 1536px the rail has no room in the margin, so it becomes the collapsed "On this page" disclosure above the content, open by default. That is the same breakpoint the main site uses for its table of contents (Tailwind 2xl, 1536px).

Scientific writing

Everything a paper needs, prefixed rd-, with automatic numbering for equations, figures, tables and theorems. Math is KaTeX (pinned 0.16.27). In Markdown posts use $…$ inline and $…$ for display, and escape a literal dollar sign as \$ (an unescaped $5 … $7 is parsed as a formula). In standalone HTML, pre-render with katex.renderToString at build time and link katex.min.css, so the page needs no JavaScript for math.

Tabbed pages

A page with tabs (a role="tablist" bar and one .rd-tabpanel per tab) follows one history rule. The reference is the tab script of research/brev-tree-benchmark, which is copied into the page, not into this template. pnpm check:report-history asserts the rule on every built page that has a tab panel.

  • The state lives in the URL. The tab, the filter and the paging are the query string: ?tab=results&filter=confirmed&shown=16. A section is the hash (#h-board). Tabs, filters and paging are real links (<a role="tab" href="?tab=results">), so the browser navigates and keeps its own history: one entry per click, no script.
  • A section jump inside the current tab (an "On this page" link, an in-page cross-reference, a card) is one history.pushState entry with the hash and the scroll. None when the view is already there. A section in another tab is a real navigation to ?tab=<tab>#<section>.
  • Back, Forward, reload and bfcache restore re-sync the tab, filter, section and scroll from the URL and the entry's state. They never add an entry. replaceState only saves the scroll position into the current entry, and maps a legacy hash-only tab URL (#results) to ?tab=results on load.
  • Scroll is restored from the entry's state, so the page sets history.scrollRestoration = 'manual' and restores with behavior: 'instant'.
  • A deep link (#h-board) opens its tab, scrolls the section below the bar after layout, and moves focus to its heading (tabindex="-1").
  • Arrows, Home and End on the tab list move focus; Enter and Space follow the focused tab. Reduced motion turns smooth scrolling off.

Checklist for a new report

  • Math, citations, numbered equations and theorems follow the Scientific writing section; escape literal $ in Markdown.
  • Link or inline research.css; body rd-body, content in rd-container (wide only if justified, and say why in a comment).
  • Experiment pages: the sticky rd-expnav directly under <body> (one gap under the sticky navbar), one link per rd-section__head with an id, and the scroll-spy script from the template.
  • Icons: Lucide only, as #i-<name>, with the page inside the lucide-sprite markers (run node scripts/build-lucide-sprite.mjs).
  • Title and page heading carry created YYYY-MM-DD · updated YYYY-MM-DD.
  • Colors only via --rd-*; charts use the sequential or categorical palette.
  • No iframes; no dependence on a host runtime; navigation that users trigger creates history entries.
  • Tabbed pages follow the history rule in the Tabbed pages section; pnpm check:report-history passes.
  • Caveats and unvalidated results are stated on the page, not buried.
  • Check both themes and a 375px viewport before publishing.

Conformance

Every standalone page under public/research/ and public/experiments/ is measured in a real browser by pnpm check:design-system (after pnpm build, about 35 seconds). The reference is the main site's post page, /posts/rust-learnings/, rendered in the same run, so the check follows theme changes on the main site. Each page is measured at 1280, 1440 and 1920 px, light and dark, plus 375 px for overflow and tap targets. Non-origin requests are blocked during the run, and the navbar must not move when a scrollbar appears.

Exceptions

  • A page-wide, documented exception: <meta name="ds-allow" content="rule-id: reason">. The reason is required.
  • An element-level exception: data-ds-allow="rule-id" on the element or an ancestor (rules colour-tokens, icon-sprite, tap-target). Use it for a chart or a diagram with its own colours, and say why in a comment.
  • A page that uses rd-container--wide must say why in a source comment next to it.

Baseline policy

Violations that exist today are listed in scripts/design-system-baseline.json, one entry per page and rule, with an owner (EcoSimulation, Brev or site) and a real reason. The rule is a ratchet: a new violation fails CI, and an entry that no longer fires fails CI until it is removed. Fix the source project or this repo, then delete the entry in the same PR. Locally, pnpm check:design-system --update-baseline adds new findings with a placeholder reason and drops fixed ones; the reasons must then be written by hand before the PR. Warnings (not failures): a missing <meta name="ds-contract"> version marker, and inline CSS over 80 KB.
