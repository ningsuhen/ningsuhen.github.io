Question and status

The question

Can a program and its models ship as one artifact and answer typed decisions on the GPU, with no third-party runtime and no silent fallback?

Status

Correctness and packaging: yes, on Metal and Chrome. Speed: not yet. The decide is 13.5× over target and decode runs at a quarter of the candle reference. CUDA waits on NVIDIA hardware.

How to read it

Shipped means merged behind a gate. Proposed means designed, not built. Estimates are labelled. All timings come from one Apple M4 Max, many under heavy GPU contention.

Findings

  • One WGSL source decodes correctly on Metal and in Chrome

    Nine hand-written kernels, fp16. SmolLM2-135M and Qwen3-0.6B match the fp32 golden on 100 prompts on both targets, diverging only where the reference's own top-2 gap is under 0.05.

    M1 · STATE.md Measurements

  • The single-file artifact works past the 1 GiB wasm cap

    Code first, weights in a trailing custom section. One GET is split mid-stream: the prefix compiles, the weights stream to the GPU through one 16 MiB chunk. Cold, OPFS-warm and device.lost reloads all match the golden 64/64.

    M2 · tools/testbench/m2-demo-results.json

  • Typed decisions run on the GPU with zero flips

    The 28-layer encoder and its typed head answer 256 questions about one document in one pass: 0 decision flips vs fp32 wherever the reference margin exceeds 0.05. #[lpm::decide] expands to that call; thresholds live in the artifact.

    M3 · B4 decision tester

  • The decide is 13.5× too slow, and the GEMM is the wall

    Candidate-row head, prefix-KV reuse, batched prefill and an attention rewrite took it from an estimated 30 s to 135 ms. The GEMM is kernel-bound (dispatch is 6% of its cost) and first measured at 0.13 TFLOPS against a plan that assumed 4. Tuning is parked until the GPU is quiet.

    D17 · decide-target steps 1–6

  • Small frozen heads beat prompting a 0.6B decoder by 40–93 points

    On intent, extraction and Rust error classes, a frozen encoder plus a kilobyte-to-megabyte head wins. Merging modules, distilling them into one student, and compiling the instruction into weights all lost.

    E9, E10a–e · STATE-T.md B7

  • Escalation memory cuts tier-2 calls by 30%

    Pre-registered on fresh seeds: refitting the cheap head on teacher labels cut escalation from 30.2% to 21.2% with accuracy flat. Tier 2 is an encoder head (Qwen3-Embedding). A 4B ties it only with retrieved labelled examples, at about 150× the latency, so it goes to tier 3.

    E11a, E11c · Intelligence

  • The stored thresholds don't deliver their precision

    D16's unlabelled 10th-percentile cut gave 91.7% where 97% was meant. Ten labelled rows per class fix it on familiar traffic. On unfamiliar phrasing, no cut holds 97% without answering far less.

    E11-T · D16

  • Modules cannot yet say "not mine"

    No out-of-scope detector held false-accepts under 5% while keeping half the in-scope traffic. Every module must name an escalation target.

    E10b

Model calls as typed functions

Models are programming primitives (decide, extract, constrained generate), not chat. "Large" is the program, not the model: a 0.4B encoder and a 0.6–1.5B decoder wired into code. A call returns Decision<T>: a value with a margin (top-1 minus top-2), or Unresolved. There is no confidence field. In the prior prototype, calibration buckets sharpened temperature about 10×, so a calibrated 0.24 read 0.99 and the confidence gate never fired. Margin survives any monotone temperature change.

#[derive(lpm::Choice)]
enum Route {
    #[criteria("invoices, payments, refunds")] Billing,
    #[criteria("how-to questions")] Support,
}

#[lpm::decide(instructions = "Which department should handle this ticket?")]
fn route(ticket: &str) -> Decision<Route>;

match route(&lpm, &ticket).await? {
    Decision::Resolved { value: Route::Billing, margin }
        if margin >= lpm.threshold("route") => billing(&ticket),
    _ => escalate(&ticket),   // Unresolved and low margin both land here
}

E9: prefix KV stays

The 607-token instruction (77 numbered intents) was compiled into a 16-token soft prompt plus a rank-16 LoRA, distilled from the prefix-KV model. It matched 96.8% of the teacher's training decisions and then flipped 17.95% of held-out ones. As a standalone classifier it was decent, 90.4% accurate on what it resolved, but it is not the same function, so it cannot replace the prefix.

Caught before they became results

  • The first 4B teacher broke 59% of right answers. Batched and one-at-a-time scoring agreed on 148 of 150 rows, so padding was cleared; bare intent names were the cause.
  • E11a first passed on a test set where 60% of rows were near-copies of training rows. Deduplicated, it passes only narrowly.
  • A "filtering wins" reading was picked after seeing seeds 0–2. The pre-registered run on fresh seeds reversed it.
  • E11c's first run scored every head at 0% accuracy: a tuple was unpacked in the wrong order.
  • E10d first came back at chance: the split shuffled texts without their labels.
  • The E10d generator looped for 3 h: rustc was given no input, so every sample "compiled". It now fails closed.
  • E10e's LoRA arms first read features at layer 8 or 12, below the LoRA on layers 24–27, so the adapter got zero gradient. Gradient-checked and moved to the final layer.
  • The feature cache was keyed by split and size only, so reordered data would have reused stale features. It now hashes the content.

Does a 97% cut deliver 97%?

E11 asks what should happen to the rows a cheap module is unsure of. The setup is the same throughout. On BANKING77, a TF-IDF character n-gram head trained on 50 labels per class answers when its top-2 margin clears a cut, and escalates otherwise. Every cut is chosen on a labelled calibration split (CAL), never on test. The runs were offline Python, on CPU plus one shared RTX 4060.

The unlabelled cut fixes coverage, not precision: it fell short in 20 of 20 repeats. Five labelled rows per class missed 96% in 15% of repeats; ten held. 60% of BANKING77's test rows have a train near-copy at cosine 0.90 or above. On the rest, a cut tuned on random rows overshoots, and deduplicating CAL restores precision at roughly half the coverage. A sibling project held out whole template clusters and found coverage under 3%. A head can promise 97% only on traffic that resembles what it was trained on.

Who takes the escalated rows

The head's top-15 shortlist held the right intent 97% of the time, so the misses belong to the reader. A 4B reading bare names breaks more right answers than it fixes. Rules help. Eight retrieved labelled examples help most, cutting broken answers from 55% to 15%. That ties the Qwen3-Embedding head (−0.027, CI −0.068 to +0.014), at 184 ms per row against about 1 ms. On unfamiliar rows the encoders slip and the example-fed reader holds: it beats MiniLM there by 0.100 (CI +0.017 to +0.183). Given LPM's exact prompts, a second 4B (Qwen3-4B-Instruct-2507, llama.cpp) ranked the prompts the same way: examples +0.304, rules +0.128, names −0.065. The plan that follows: an encoder head for tier 2, and a 4B with retrieved examples for tier 3.

Memory loop, pre-registered

E11c, pre-registered before the run, fresh seeds 3–5. Memory refits the head's final layer on teacher-labelled escalations; the vectorizer stays frozen. Four rounds of traffic, about 300 rows each. Pass: accuracy within 0.5 points of round 0, and an escalation cut at least half the gold-label cut.
Labels in memoryLabels wrongEscalation, round 0 → 4Share of gold cutAccuracy changeVerdict
Gold (ceiling, diagnostic only)0%30.2% → 18.3%100%+0.37—

Accuracy barely moves, even with gold labels, because the teacher already answers the hard rows. A better head just keeps more of them local. So the loop pays in cost, 30% fewer tier-2 calls, and earlier runs that judged it on accuracy read it as flat. Keeping only the teacher's confident labels looked better on seeds 0–2 and lost on two of three fresh seeds: volume of labels beat their cleanliness. A kNN memory overfit, gaining 8.6 points on traffic it had seen while held-out accuracy stayed flat.

Where the evidence disagrees

Where the outside evidence disagrees with us

Megakernels beat kernel-per-op on CUDA, but each one relies on device-side scheduling that WebGPU lacks, so D5 stands for WGSL. A 2026 paper finds single-stream WebGPU inference bound by per-dispatch cost. Ours splits: the decide's GEMM is kernel-bound (dispatch is 6% of its cost), while the encoder's non-GEMM layers are launch-bound (~456 dispatches at ~84 µs).

Gaps. Nothing measures a candidate-row head on WebGPU or Metal. No recent source compares margin with max-softmax for LLM selective prediction. No work on multi-task heads over a frozen sub-500M encoder.

Read this first

Read this first

One machine, one shared GPU. Many timings were taken at load averages of 100–330 while a 30B teacher ran on the same GPU. Correctness counts don't depend on load; absolute timings do, and the GEMM is parked until a quiet window.
  • No CUDA number exists. M4 waits on NVIDIA hardware.
  • The 256-question encoder golden is synthetic, with no ground-truth labels. The stored thresholds are each bucket's 10th-percentile margin, a stand-in for an error-based cut.
  • E10d's held-out set is 248 samples, about ±6 points.
  • The 30B teacher agreed with the trained heads only 51–69% of the time zero-shot, so E10a scored against gold labels, not the teacher.
  • Chrome supports subgroups, but wgpu's WebGPU backend cannot request the feature. Browser kernels use shared-memory reductions; the faster subgroup kernels are native-only.
  • The 1.4 GiB browser load (25.7 s) is ~15× slower per byte than the raw-byte probe. The cause is not yet measured.
  • The fast-path latency table in the brainstorm (6–10 ms) is an estimate. It assumed 4 TFLOPS; the first measured GEMM did 0.13.
  • E11 is one dataset (BANKING77), run in Python, not on LPM kernels. The tier-2 comparison is seed 0. The example-fed 4B's lead on unfamiliar rows rests on 120 rows and needs more seeds.
  • The 4B ran without its fused linear-attention kernels, so its 124–1,062 ms per row are upper bounds. E11c's Qwen3-Embedding features came from fp16 on GPU; against fp32 they agree at cosine 0.9999 and flip 2 of 200 predictions.
